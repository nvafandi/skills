# Module: Refactor Plan

Create and maintain `refactor-plan.md` — the living execution document written into the **target project root**. The plan mirrors the 20-phase flow of SKILL.md exactly: same order, same stages, same gates, pre-filled with project-specific scope so every phase is executed clearly and deliberately.

## Lifecycle

| Moment | Action |
|---|---|
| **Phase 3** (Analysis Report) | **Create** `<project-root>/refactor-plan.md` from the template below, filled with Phase 1–2 results. Present it together with the analysis summary — the user approves the plan at this gate. |
| **Every phase (P04–P18)** | **Update**: flip that phase's status checkbox, fill its *Result* line, append a row to the Completion Log. Do this before printing the progress card. |
| **Phase 19** | **Freeze & cross-check**: every phase must be `[x]` or `[-]`; unresolved items move to the Deferred registry with reasons. Link the plan from the Refactoring Report. |
| **Phase 20** (if git accepted) | The plan is part of the commit — it documents what was planned vs done. |

If `refactor-plan.md` already exists at the project root (previous run), ask the user: archive the old one to `refactor-plan-<YYYYMMDD-HHmmss>.md`, resume it, or overwrite.

## Status Legend

Use exactly these markers in phase status lines:

- `[ ]` pending — not started
- `[~]` in progress
- `[x]` done — gate passed (or SKIP justified)
- `[-]` skipped — record reason inline

## Rules

1. **Never reorder or renumber sections** — reviewers diff consecutive runs against the same shape.
2. Every finding in §2 must name its target phase; every phase's "Scope here" cites finding IDs (F1…) or states "none detected".
3. Update statuses **during** the run, not retroactively — the plan must always reflect reality if the session dies mid-run.
4. The Completion Log is append-only; corrections are new rows, not edits.
5. Keep evidence as `path:line` so any finding can be verified without re-scanning.
